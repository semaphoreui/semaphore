# Encryption keys — separate keys file, purpose split, content-addressed ids, hot rotation

Semaphore encrypts Access Key secrets and the `jwt_signing_key` DB option with AES-256-GCM. One
inline key (`access_key_encryption` / `SEMAPHORE_ACCESS_KEY_ENCRYPTION`) used to serve both, was
reachable through the process environment and could only be rotated offline with
`vault rekey --old-key`. Now the keys live in a dedicated file (`encryption.keys_file`) split by
purpose (secrets vs options), every ciphertext carries a fingerprint of the key that wrote it, and
an edit to the file applies without a restart.

Status (2026-09-27): implemented — add2f0fb6 (2026-06-19, phase 1: keys file, purpose split,
hot reload, `vault check`, rekey backup/rollback, JWT rekey), 93ff968a0 (2026-06-20, phase 2:
key-id keyset replacing primary/secondary trial decryption), e862a0700 (2026-06-22, active
pointer fields renamed); on `origin/2-19-stable`, in tag trees from v2.19.5-beta1; operator docs
in `docs/docs/admin-guide/security/encryption.md`, reference pages generated by `task docs:gen`.

## Decisions and why

- Keys file separate from the main config, as GitLab keeps `gitlab-secrets.json` apart from
  `gitlab.rb`; per-key `file:` references so each key can be its own secret mount. Parsed as YAML
  (a superset of JSON) regardless of extension because Kubernetes secret mounts have none. An
  inline `encryption_keys` section in the main config was rejected — the file is the only place.
- Purpose split: `secret_key` protects Access Key secrets, `option_key` protects DB options (the
  JWT signing key), each rotatable alone. Option falls back to the secrets key when unset so an
  existing `jwt_signing_key` keeps loading; `vault rekey` migrates it. The flat legacy fields
  `access_key_encryption` / `option_encryption` still work as single non-rotating keys.
- Keyset, not keyring: the file is a registry — inline `keys:` map and/or a `keys_folder:` of
  one-file-per-key, combined — plus `active:` pointers per purpose (label, or `*_file` filename
  relative to the folder). Every non-active key stays decrypt-capable, so "retire" = stop being
  active. This replaced phase 1's `primary`/`secondary` trial decryption, which was O(keys), could
  not say which key wrote a row and could not prove a key unused before removal.
- Key id derived from material — `base64url(SHA-256(raw key))[:8]` in `util/keyid.go` — never
  operator-chosen: a label stored in the DB and repointed at other material would silently
  mis-decrypt, while a derived id fails loudly ("key id … not found"). Labels and filenames are
  human-only and never stored. 8 bytes is ample (birthday bound about 2^32 keys). Same idea as
  `computeKID` in `pkg/jwt/signer.go`.
- Envelope `<id>:<base64(nonce||ct)>` inside the existing `secret` string — no DB column
  anywhere. `:` occurs in neither part; `isKeyID` demands the exact id length so a stray colon in
  legacy data (a PEM `Proc-Type:` line) is not misread. No prefix = legacy, decrypted by trial:
  flat key first, then every registry key (option: flat option, flat access, registry).
- Flat fields are registered as keys labelled `""` so new writes can stamp them, yet they never
  satisfy a named active pointer. Structured wins over flat; a "mismatch = error" rule was
  rejected because it would block hot rotation.
- Hot reload with no globals: an immutable keyset behind an atomic pointer on `Config`;
  `reloadMu` serialises SIGHUP and poller; the read path never locks. Invalid keys panic at boot;
  a failed reload leaves the active keyset untouched. Polling by content (default 15 s, `0` =
  SIGHUP only, off automatically without a keys file) rather than fsnotify: survives the atomic
  symlink swap of Kubernetes mounts, adds no dependency, and catches edits to referenced key
  files. No separate `keys_poll_enabled` flag.
- `vault check` counts rows per key id without decrypting: active / retired, rekey pending /
  retired, SAFE TO REMOVE / legacy (no id) / MISSING KEY (non-zero exit), plus the JWT option's
  slot. `vault rekey` re-stamps rows to the active id and then runs `RekeyJWTSigningKey` (the
  old rekey skipped the option — a real bug); `--old-key` for un-prefixed data;
  `--backup`/`--rollback` snapshot ciphertexts as JSONL; external-storage keys are skipped.
- Phase-1 file shape (`access_key: {primary, secondary}`) was dropped instead of dual-parsed
  because phase 1 never shipped.
- `KeySource.File` is a path and not `,sensitive`; `Value` and the flat fields are. Material is
  validated by `validateAccessKeyEncryption` before it enters the registry.

## Open, broken or deferred

- ⚠️ 2026-09-27: names diverge from the plan and the seven keyid tasks — active pointers are
  `active.secret_key` / `secret_key_file` and `option_key` / `option_key_file`, not
  `access_key`; the `keys_folder` registry and the `*_file` pointers go beyond the plan.
- ⚠️ 2026-09-27: the phase-1 shape is not rejected loudly as task 6 required —
  `readEncryptionKeysConfigFile` unmarshals non-strictly, so an old-shape file yields an empty
  registry and the server silently runs on the flat fields.
- ⚠️ 2026-09-27: no `encryption-config.yml` example was ever committed and `.gitignore` has no
  keys-file entry (task 7); the docs page holds the only examples.
- `vault check --verify` (decrypt a sample to prove the file holds the right bytes) not built.
- Not built: external KMS/Vault as a `KeySource`; cookie key rotation (`CookieHash`,
  `CookieEncryption`, `securecookie` in `util/config.go`); an admin API or UI reload button;
  online/background rekey for very large installs.
- Task-owned survey-secret rows (`AGENTS/work/secrets-and-task-vars/survey-secrets-remote-runners.md`)
  are re-stamped by rekey like any other row.
